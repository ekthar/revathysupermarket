# Swiggy-parity overhaul: database-first data, product variants, animation migration, and funnel analytics

This change converts a demo-first Next.js storefront into a production-ready application across 8 coordinated phases. The database becomes the primary data source (with demo data gated behind `NEXT_PUBLIC_USE_DEMO_DATA`), a `ProductVariant` model lands with migration and variant-aware cart, the GSAP `ScrollReveal` in the product section is replaced by Framer Motion `whileInView`, and the homepage gains new merchandising surfaces (offers strip, time-of-day rail, brand rail). A design system consolidation removes ~27% of `globals.css` by deleting unused utility classes and unifying shadow tokens. Accessibility gets a screen-reader announcement system and axe-core CI gating. Funnel analytics events are wired through the checkout flow.

Watch for: cart validation API doesn't reconcile variant-level stock (confirmed), `variantLabel` column added to `OrderItem` schema but never written during order creation (confirmed), time-of-day rail renders server-side with `revalidate: 60` so the time slot can be stale for up to 60 seconds at slot boundaries (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The database-first strategy is clean: every fallback site consistently gates on `useDemoData`, and the PDP now queries related products from the DB with proper filtering. The `generateStaticParams` removal in favor of dynamic rendering is the right call given the DB-first posture.

The cart keying scheme (`productId::variantId`) threads through add, remove, update, and granular subscription hooks without breaking the existing product-id-only flow. However, the hydration reconciliation logic (`/api/cart/validate`) still only validates product-level stock, creating a correctness gap where a specific variant can be out of stock while the product aggregate shows availability.

The design system consolidation removes dead CSS and replaces shadow references with `shadow-elevation-1`. The scope is large enough that admin components sharing these class names could silently lose styling — worth a visual regression sweep on dark mode.

The funnel analytics instrumentation covers category view, cart view, checkout step completion, and search zero-results. The `CART_VIEWED` effect has a stale-closure risk: it may fire before cart hydration completes (seeing zero items) and never re-fire, losing the event entirely.

<details>
<summary>Issues (6)</summary>

1. **Cart validation ignores variant stock** — `/api/cart/validate` only checks product-level stock. A variant can be out-of-stock while the product isn't, so the reconciliation won't remove the stale variant item. Extend the validate endpoint to accept variant IDs and check `ProductVariant.stock`.
2. **`variantLabel` never persisted to orders** — The `OrderItem.variantLabel` column exists in the migration but the order-creation API never writes it. Wire `variantLabel` through the checkout submission so order history displays the chosen variant.
3. **Time-of-day rail caching mismatch** — `getTimeSlotKey()` runs server-side at render time and the page uses `revalidate: 60`. At slot boundaries (e.g., 10:59→11:00) the rail title can be stale for up to 60 seconds. Either make this a client component or reduce `revalidate` for the slot-relevant section.
4. **CART_VIEWED fires with stale closure** — The `useEffect` in `cart-page-client.tsx` uses `items.length` and `subtotal` from the render that mounted the component but has an empty dependency array. If the cart hydrates from localStorage after mount, the effect sees zero items and never fires. Depend on `hydrated` state with a ref guard.
5. **ZeroResultSuggestions always receives empty `popularProducts`** — The component accepts a `popularProducts` prop but is always called with `[]` in global-search. Either pass actual popular products or remove the prop to avoid dead code.
6. **`isDefault` variant field unused** — The `ProductVariant.isDefault` column exists but the PDP default selection logic picks the first in-stock variant by `sortOrder`, ignoring `isDefault`. Either use it or drop the column to avoid confusion.

## Variant-aware cart keying and stock gap

The composite key pattern `productId::variantId` is consistent across `addItem`, `removeItem`, `updateQuantity`, `useCartItem`, and the cart page UI. The gap is in hydration reconciliation. When the cart rehydrates from localStorage, `cart-provider` calls `/api/cart/validate` with an array of product IDs (extracted via `item.id`). The validate endpoint queries `Product` stock, not `ProductVariant` stock:

```typescript
// cart-provider reconciliation:
body: JSON.stringify({ ids: snapshot.map((item) => item.id) }),

// validate/route.ts — only queries Product table:
const products = await prisma.product.findMany({
  where: { id: { in: ids } },
  select: { id: true, name: true, stock: true, ... },
});
```

If a user has "Milk 500ml" variant in cart with 0 variant stock but the parent product "Milk" still has aggregate stock > 0 (from the 1L variant), the reconciliation won't flag it. The cart will show the item as valid until checkout, where server-side order creation should re-validate — but that's a fail-open gap for the cart UX that creates a worse error experience at the latest possible moment.

## Order item schema without write path

The migration adds `variantLabel TEXT` to `OrderItem` and the schema declares the field. The order-creation API route (not in this diff, pre-existing) has no awareness of `variantLabel` or `variantId`. The column will remain NULL for all orders involving variants until wired through. This means order confirmation, history, and admin order views won't show which variant the customer chose.

## Time-of-day rail server-render timing

`TimeOfDayRail` is a Server Component calling `new Date().getHours()`. The homepage has `export const revalidate = 60`. At slot boundaries (e.g., 10:59→11:00) the cached response still shows "Breakfast Essentials" with dairy/beverage products for up to 60 seconds. Acceptable for an MVP where the product overlap between slots is high, but becomes a user-facing inconsistency as the slot product mix diverges.

## CI Lighthouse without database

The Lighthouse job builds the app with `SKIP_ENV_VALIDATION=1` but without a `DATABASE_URL`. Pages like `/products/robusta-banana` hit DB queries wrapped in `.catch(() => null)`, so the build succeeds but produces empty/fallback-state pages. Lighthouse then measures performance of an error state rather than the actual product page. This won't block CI (the performance score for an empty page is high) but makes the budget assertion meaningless for those routes.

## Analytics: stale closure in CART_VIEWED

```typescript
useEffect(() => {
  if (items.length > 0) {
    trackEvent(ANALYTICS_EVENTS.CART_VIEWED, {
      itemCount: items.length,
      cartTotal: subtotal,
    });
  }
}, []); // eslint-disable-line react-hooks/exhaustive-deps
```

The cart hydrates from localStorage asynchronously. If `items` is still empty at mount time (before hydration completes), the condition fails and the event is never sent. A safer pattern: depend on the cart's `hydrated` state and fire once after hydration with a ref guard to prevent double-fires.

## `popularProducts` dead prop

The `ZeroResultSuggestions` component in global-search is always called with `popularProducts={[]}`. The "Popular products" section renders conditionally on array length, so this code path is unreachable. Either wire it to actual data or remove the prop to avoid giving future developers the impression it's functional.
